# pharma-qc-analytics

A **dbt** project modeling batch release testing for a pharmaceutical
quality control (QC) lab: batches, specifications, test results, and
deviations, rolled up into the metrics a QC/manufacturing team actually
watches — out-of-specification (OOS) rate by test, batch release
disposition, and deviation cycle time. Runs anywhere with zero setup
using [DuckDB](https://duckdb.org/) as the local engine: no warehouse, no
credentials, no Docker.

## Why this exists

I work in QC for a biopharmaceutical manufacturer. This project applies
that domain knowledge to a standard dbt workflow — the kind of batch
release and OOS-trending analysis I'd build for a quality or manufacturing
analytics team — on a fully synthetic dataset. **No real company,
product, test data, or specification in this repo is real.** Product
names, lot numbers, spec limits, and results are all generated by
`scripts/generate_seed_data.py`.

## Domain model

```
seeds/raw_products        seeds/raw_specifications
seeds/raw_batches          seeds/raw_qc_results   seeds/raw_deviations
        │                        │                        │
        ▼                        ▼                        ▼
  staging/stg_*  (clean, rename, cast — 1:1 with sources)
        │
        ▼
  marts/fct_qc_results   (grain: one row per test result, joined to its spec limits)
        │
        ├──► marts/dim_batches               (per-batch rollup + release disposition)
        ├──► marts/oos_rate_by_product_test   (OOS rate per product × test)
        └──► marts/deviation_cycle_time       (monthly deviation volume & time-to-close)
```

- **`fct_qc_results`** is the central fact table: every test result,
  joined to the batch it came from and the specification (lower/upper
  limit) it was judged against. It also computes
  `pct_of_spec_width_used` — where a result falls across a two-sided
  acceptance window as a percentage (0% = at the lower limit, 100% = at
  the upper limit) — a single comparable number across tests reported in
  completely different units (%, AV, mg/mL...). See
  `macros/pct_of_spec_width.sql`.
- **`dim_batches`** rolls results and deviations up to one row per batch
  and derives a `release_disposition` (`Released` /
  `Released with deviation` / `Rejected`).
- **`oos_rate_by_product_test`** is the metric a QC trending review
  actually reads: which product/test combinations are generating the
  most OOS results, and how close the *passing* results are running to
  the edge of spec (`avg_pct_of_spec_width_used`) — a classic early
  warning sign of a drifting process before it starts failing outright.
- **`deviation_cycle_time`** tracks monthly deviation volume and
  average/overdue time-to-close by category — a standard quality-systems
  KPI (deviations are generally expected to close within 30 days).
- **Tests**: `not_null`/`unique` on every primary key, `relationships`
  tests tying results and deviations back to a real batch,
  `accepted_values` on `status` and `release_disposition`, and a singular
  test (`tests/assert_no_result_outside_recorded_range.sql`) that checks
  a result's `Pass`/`OOS` status actually agrees with the spec limits it
  was joined to — the kind of data-integrity check that matters a lot
  more in a regulated QC context than in most domains.

## Data

All data under `seeds/` is **synthetic**, generated by
`scripts/generate_seed_data.py` (Python standard library only — no
third-party packages, no network, deterministic via a fixed random
seed):

```bash
python3 scripts/generate_seed_data.py
```

It produces 5 fictional products, 200 batches (40 per product) spanning
Jan 2024–Nov 2025, a 5-test release panel per product (25 specs total,
mirroring a typical tablet/capsule release panel: assay, dissolution,
impurities, water content, content uniformity), 1,000 test results, and
61 deviation records. The generator biases results to a ~1.8% OOS rate
and a small share of "near the limit but passing" results, roughly
matching real-world release-testing pass-rate profiles.

## Running it

Requires Python 3.9+ and pip with normal internet access (to install dbt
itself — the project's own data and logic need nothing else):

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install dbt-core dbt-duckdb

dbt seed    # loads the CSVs in seeds/ into DuckDB
dbt run     # builds staging views + mart tables
dbt test    # runs all schema + singular tests
# or just:
dbt build
```

dbt finds the `profiles.yml` in the project folder automatically when you
run it from the project root. This creates a local `pharma_qc_analytics.duckdb`
file — nothing leaves your machine. dbt builds into three schemas:
`main_raw` (seeds), `main_staging` (views), and `main_marts` (tables).

### A few questions this model answers directly

Open the database with the DuckDB command-line tool
(`duckdb pharma_qc_analytics.duckdb`), then:

```sql
-- which product/test combinations are closest to needing attention?
select * from main_marts.oos_rate_by_product_test order by oos_rate_pct desc limit 5;

-- how many batches shipped with a deviation on the books?
select release_disposition, count(*) from main_marts.dim_batches group by 1;

-- which deviation categories blow past the 30-day close target most often?
select category, sum(overdue_30day_count) from main_marts.deviation_cycle_time group by 1 order by 2 desc;
```

## Notes on the design

- **Why DuckDB, not Snowflake**: this is a portfolio artifact meant to be
  cloned and run by anyone immediately. The SQL uses only standard
  constructs (`cast`, `date_trunc`, `date_diff`, standard joins/window
  aggregates) and would port to a warehouse-backed profile with no model
  changes.
- **Why seeds instead of sources**: in a real LIMS/MES-backed pipeline,
  `raw_batches` and `raw_qc_results` would be `sources:` landed from the
  lab's own systems, not CSVs committed to git. Seeds keep this project
  reproducible from a single `git clone`.
- **Fictional data, real structure**: the five-test panel
  (assay/dissolution/impurities/water content/content uniformity), the
  OOS-rate framing, and the 30-day deviation-closure KPI all reflect how
  this kind of data is actually structured and reviewed in a GMP QC
  environment — only the specific products, lots, and numbers are made up.
